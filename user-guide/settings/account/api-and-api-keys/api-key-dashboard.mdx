## Overview

An API key is a unique identifier that authenticates and authorizes requests to MoEngage API resources. Use the API Key Dashboard to create keys, scope each key to the APIs it needs, and regenerate or archive keys as your integrations change.

The multi-API key feature is currently supported for the following API groups:

| API Group | Supported Authentication Types |
| --- | --- |
| [Data APIs](/api/data/data-overview) | Basic Auth, OAuth 2.0, AWS STS Auth |
| [Segmentation APIs](/api/custom-segments/custom-segments-overview) | Basic Auth |
| [Push APIs](/api/push/push-overview) | Basic Auth (Legacy) |
| [Campaigns](/api/campaigns/campaigns-overview) | Basic Auth, OAuth 2.0, AWS STS Auth |
| [Inform](/api/inform/inform-overview) | Basic Auth |
| [Offerings](/api/offerings/offerings-overview) | Basic Auth, OAuth 2.0 |
| Decision Policy | Basic Auth, OAuth 2.0 |
| [Dashboard & Analyze](/api/analytics/analytics-overview) | Basic Auth, OAuth 2.0 |
| Channel Configuration | AWS STS Auth |
| [Personalize](/api/personalize-experience/personalize-overview) | AWS STS Auth |

<Note>
 - Segmentation APIs and Inform are available only with Basic Auth.
 - Channel Configuration and Personalize are available only with AWS STS Auth.
 - Creation of new API keys for Push APIs is not currently supported. Push APIs work only with **Basic Auth (Legacy)** keys migrated to this dashboard.
</Note>

To send data to MoEngage, you can use the Workspace ID and key for that particular API. Whenever a key is regenerated, the old key expires immediately and it takes some time for the new key to become functional, which may result in service interruptions. MoEngage provides multiple API keys to help you avoid this situation:

- **Generate a new key while the existing key is still available**: With multi-key support, the existing key remains active until the new key becomes functional. This allows you to rotate keys for security purposes without causing downtime. For example, if your team needs time to integrate a new key, the old key continues to work during that period. After the new key is integrated, you can archive the old one.
- **Use different keys for different teams**: You can create separate keys for different internal teams or external vendors, each scoped to the APIs they need. This provides granular access control and improves security across your organization.

To restrict which IP addresses can use your keys, see [API Firewall](/user-guide/settings/account/security/api-firewall).

## Authentication Types

MoEngage supports the following authentication types for API keys:

- **Basic Auth**: The standard authentication method, which uses an API key and secret. Choose this method for server-to-server integrations that do not need token expiration.
- **OAuth 2.0**: A token-based method that issues short-lived access tokens. You set the token expiry time, and MoEngage validates each access token automatically. For the full flow, including generating, using, and refreshing tokens, refer to [OAuth 2.0 Overview](/api/oauth/oauth-overview).
- **AWS STS Auth**: A token-based method for workloads that run on AWS. Instead of a shared secret, you allowlist the AWS Security Token Service (STS) assumed-role ARNs that can use the key. Choose this method when your services already assume an IAM role and you want MoEngage to authorize those roles directly. See [Add Role ARNs](#add-role-arns).

You select the authentication type from the **Authentication type** list in the **Create new key** dialog. You cannot change the authentication type after you create the key. To move an integration to a different authentication type, create a new key and archive the old one.

## Create a Key

<Info>
  - After the multi-API key feature is enabled, the existing API keys in the API dashboard are migrated to your new API key dashboard as legacy keys.
  - You can view the legacy key (autogenerated previously when the workspace was created and migrated to this new dashboard) details and continue to use them. However, archiving, editing, and regenerating legacy keys is not supported.
  - MoEngage recommends creating and using new keys, as legacy keys will be deprecated in the future.
</Info>

  </Step>
  <Step title="Choose an Authentication Type">
    From the **Authentication type** list, select the method you want to use, then set the options for that method:

        2. Under **Select APIs for access**, select the API groups you want to access using this key:
           - Data APIs

           - Offerings
           - Decision Policy
           - Dashboard & Analyze

         <Frame><img src="/images/oAuth20.png" alt="Image showing the steps to create a new API key in the Create new key dialog for OAuth 2.0" /></Frame>

For per-endpoint request limits and payload caps, see [Rate Limits](/api/rate-limits).

## AWS STS Auth

This section applies only to keys that use the **AWS STS Auth** authentication type. MoEngage authorizes such a key against a list of assumed-role ARNs, and only a caller whose assumed-role ARN appears on the key can use it.

### Add Role ARNs

You create and manage these roles in your own AWS account. MoEngage does not generate the ARN, so copy it from your AWS account and paste it into the key. For more information, see the [AWS Security Token Service API Reference](https://docs.aws.amazon.com/STS/latest/APIReference/Welcome.html).

#### ARN Format

Enter each ARN in the following format:

```text
arn:aws:sts::<aws-account-id>:assumed-role/<RoleName>/<RoleSessionName>
```

| Segment | Description |
| --- | --- |
| `aws:sts` | The service. An AWS STS Auth key accepts Security Token Service ARNs only. |
| `<aws-account-id>` | Your 12-digit AWS account ID. |
| `assumed-role` | The resource type. The dashboard rejects ARNs that use `role` or any other resource type. |
| `<RoleName>` | The name of the IAM role your workload assumes. |
| `<RoleSessionName>` | The role session name, or `*` to match every session of that role. |

For example:

```text
arn:aws:sts::123456789012:assumed-role/MoEngageIngestionRole/data-pipeline-prod
```

#### Match All Sessions of a Role

Each session of a role produces a different ARN, so a role that many workloads or team members share can exceed the limit of 10 entries. To cover every session of a role with a single entry, enter `*` as the session name:

```text
arn:aws:sts::123456789012:assumed-role/MoEngageIngestionRole/*
```

Every session of `MoEngageIngestionRole` then receives the API access you select for this key.

<Warning>
  A wildcard grants the key's full API access to every session of the role, so use one only when every session of that role needs the same access. When you add a wildcard entry, the dashboard displays the banner **Using \* matches multiple ARNs. Ensure that this broader scope is intentional for security.**
</Warning>

When a wildcard entry already covers a role, you cannot add a named session for the same role. The dashboard treats the named session as a duplicate. Remove one of the two entries to save the key.

#### ARN Validations

| Condition | Message |
| --- | --- |
| The ARN does not match the expected format. For example, the account ID has fewer than 12 digits, the resource type is `role` instead of `assumed-role`, or the session name is missing. | **Invalid format** |
| You enter the same ARN twice, or you add a named session for a role that a wildcard entry already covers. | **Duplicate ARN detected** |
| The list already contains 10 ARNs. | The dashboard disables **+ Add value** and states that you can add up to 10 values. |

## View Active Keys

On the **API Keys** page, the **Active API keys** table shows the following columns:

| Column | Description |
| --- | --- |
| Key name | The name assigned to the key. |
| Auth type | **Basic Auth**, **OAuth 2.0**, **AWS STS Auth**, or **Basic Auth (Legacy)** for migrated legacy keys. |
| Created on | The date and time the key was created, along with the email address of the user who created it. |
| Key | The masked key value with a view button and a copy button. |
| Actions (<Icon icon="ellipsis-stroke-vertical" />) | Options to manage the key. See [Manage Keys](#manage-keys). |

You can search for keys using the search bar. The count of active keys is displayed above the table.

<Note>
  Legacy keys are listed with the auth type **Basic Auth (Legacy)**. You can view and continue to use these keys, but you cannot edit, regenerate, or archive them.
</Note>

## FAQs

<AccordionGroup>
  <Accordion title="What are legacy keys?">
    Legacy keys are API keys created automatically when the workspace was created and migrated from the older API keys dashboard to this one. You cannot edit, regenerate, or archive them.
  </Accordion>

  <Accordion title="What is access token expiration in OAuth 2.0?">
    OAuth 2.0 access token expiration is a security feature that limits how long an access token can be used to call protected APIs before it becomes invalid.

    An access token acts as a temporary digital pass. Instead of sharing your password with every app or service, the authorization server gives you a short-lived token. When that token reaches its expiration time, the API rejects any further requests and returns an `HTTP 401 Unauthorized` error.
  </Accordion>

  <Accordion title="Why does access token expiration matter?">
    - **Better security**: If an attacker steals a short-lived token, they have only a brief window to exploit it before it stops working.
    - **Resource control**: Expiration prevents unused or abandoned tokens from filling up the authorization server's database.
    - **Standard lifespan**: You can set the access token expiration anywhere from 5 to 60 minutes.
  </Accordion>

  <Accordion title="How does MoEngage handle expired tokens?">
    MoEngage issues a companion refresh token alongside the access token. Your app uses this longer-lived refresh token in the background to request a fresh access token, without forcing the user to log in again. For the refresh request and its error codes, refer to [Refresh Access Token](/api/oauth/refresh-access-token).
  </Accordion>

  <Accordion title="Where do I find my assumed-role ARN?">
    You find it in your own AWS account. Create or identify the role your workload assumes, then copy its assumed-role ARN. MoEngage does not create the role or generate the ARN. For the format MoEngage accepts, see [ARN Format](#arn-format).
  </Accordion>

  <Accordion title="How many ARNs can one key have?">
    One key accepts up to 10 ARNs. After the list reaches 10 entries, the dashboard disables **+ Add value**. To cover more sessions of the same role, use a wildcard session name instead of listing each session separately. See [Match All Sessions of a Role](#match-all-sessions-of-a-role).
  </Accordion>

  <Accordion title="Can I change the authentication type of an existing key?">
    No, you cannot change it. You can edit the key name, the expiry time, the ARN list, and the API access, but the authentication type stays as you set it at creation. To switch an integration to a different authentication type, create a new key and archive the old one.
  </Accordion>
</AccordionGroup>
