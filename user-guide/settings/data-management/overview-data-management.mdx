The Data Management feature provides a comprehensive insight into the data you track in MoEngage. The data encompasses various crucial elements, including events and user attributes. You can access this feature from **Settings** \>**Data** \> **Data Management**.

<Info>
  If you have [Portfolio](/user-guide/settings/account/portfolio/portfolio) enabled for your workspace, the Data Management will have associated changes. For more information, refer to [Portfolio: Data Ingestion and Management](/user-guide/data/key-concepts/portfolio-data-ingestion-and-management).
</Info>

Following are the key information available from the Data Management dashboard:

- Clear visibility of unique events and unique user attributes tracked for your MoEngage account out of the total allowed quota of events and user attributes.
- Displays the count of auto-blocked events and user attributes automatically blocked due to limit breach.
- Displays the volume of users and events processed through MoEngage.
- Displays the top 10 events based on volume.

The below limits apply when you track data in MoEngage:

| **Type** | **Default Limit** | **Handling for overage** |
| --- | --- | --- |
| Unique Events | 512 | Events not tracked in the last 60 days are auto-blocked first, and then new events are blacklisted if the limit is still breached. |

Setting up allowed data type action is supported for user attributes and event attributes and this ensures that any other data type is not recorded for the same attribute.

Perform the following steps to set allowed data types for event attributes or user attributes:

1. Click the ellipsis icon against event attribute, or user attribute.
2. Click **Edit attribute**.
3. In the **Edit attribute details** side drawer, select the data type from the **Allowed data type** list. <img src="/images/moengage_6c9237.png" alt="Screenshot 2025-03-10 at 4.45.39 PM.png" />
4. Click **Save.**

#### How does this work?

For example, if you set the allowed data types of an attribute called "amount" as Numeric, then after this point, whenever the "amount" attribute is tracked, MoEngage will try to typecast the value to Numeric. For example, after setting allowed data types of amount as Numeric, if you send `{"amount": "145"}`, which is a string value, we will save it as 145 numeric and enable you to run numeric operators on this value in Segmentation and Analytics. However, if you send `{"amount": "sample value"}`, we will not be able to typecast this value, and hence it will be dropped. We will not save the amount: sample\_value in your database to ensure accurate data is only saved.

The below table lists the data type of incoming attributes on columns and the allowed data type on rows and the value of each cell represents the data ingestion logic.

|  | String | Numeric | Boolean | Date | Location |
| --- | --- | --- | --- | --- | --- |
| Any | Accepted as String | Accepted as Numeric | Accepted as Boolean | Accepted as Date | Accepted as Location |
| String | Accepted as String | Typecast to String | Typecast to String | Typecast to String | Typecast to String |
| Numeric | Typecast to Numeric if possible else drop | Accepted as Numeric | Dropped | Dropped | Dropped |
| Boolean | Typecast to boolean if possible else drop | Dropped | Dropped | Dropped | Dropped |
| Date | Typecast to Date for accepted formats else drop | Dropped | Dropped | Dropped | Dropped |
| Location | Typecast to Location for accepted format else drop | Dropped | Dropped | Dropped | Dropped |

By default, attributes will be set to **Any** which means that any data type will be accepted for this attribute. If more than one data type is set for an attribute then your segmentation drop-down will show multiple data types during query creation as shown below.

![Screen\_Shot\_2021-09-27\_at\_11.31.45\_AM.png](/images/moengage_34b97a.png)

Once you set the allowed data type, only the allowed data type will be ingested going forward. However, we may still see older data types in your database due to past data present in the system. By default, the allowed data type will be pre-selected for your segmentation.

#### Effect on Data Already Ingested

Setting an allowed data type applies to data ingested after the change. MoEngage does not convert values that were already stored under the previous data type, and it does not re-ingest or rewrite past events, so an attribute keeps a mix of both data types until the older values age out of your retention window.

This has consequences worth planning for before you change the allowed data type of an attribute that is already in use:

- **Queries on the new data type match only the newer values.** A segmentation or analytics query that filters the attribute as the newly allowed data type returns 0 users, or far fewer than expected, because values stored under the previous data type are not evaluated as the new type. The count recovers as new data is ingested. This is the most common reason a segment count appears to drop right after a data type change.
- **Both data types stay available in the query builder.** The attribute keeps every data type it has ever been tracked as, so the segmentation dropdown continues to list the previous data type alongside the allowed one. The allowed data type is pre-selected, but the older type remains selectable.
- **Value suggestions still show values from the previous data type.** Suggestions are generated from data that has already been ingested, so values stored under the old data type keep appearing. They're removed only when newer values replace them after the attribute reaches its suggestion limit, or when the attribute receives no values for 60 days. For details, see [Value Suggestions](/user-guide/segment/advanced-concepts/value-suggestions).

To query the full history of an attribute while both data types are present, add one condition per data type and combine them with OR — for example, the attribute as Date for newer values, OR the attribute as String for older values.

<Note>
  Relative date operators — such as "in the last 7 days" — are available only on the Date data type. Values still stored as String cannot be filtered by a relative date, so a segment that has to cover both data types needs an absolute value or range for the String condition. Where the full history matters and relative dates are required, re-ingest the historical values in the allowed data type instead of querying across both.
</Note>

### Rules

<Note>
  This is an Early Access feature. To enable it for your account, contact your MoEngage Customer Success Manager (CSM) or the Support team.
</Note>

Rules let you enforce data standards on incoming user identifiers. When you enable a validation rule on an email or mobile number attribute, MoEngage checks every incoming value against the rule before ingestion. This reduces delivery failures and improves campaign performance.

When a validation rule is enabled on an attribute:

- Incoming values are checked against the rule before ingestion.
- Values that don't match the rule are dropped. The attribute value isn't stored, but the rest of the user record is accepted.
- Valid values are ingested normally.

<Info>
  Validation rules apply only to new incoming data. Existing user records are not retroactively validated. To clean existing data, re-import it using [File Imports](/user-guide/data/imports/setting-up-a-file-import) or update it using [Data APIs](/api/data/data-overview).
</Info>

#### Built-in Rules

##### Email

The Email rule makes sure every email is campaign-ready. It enforces RFC 5322 standards and converts each email to lowercase.

- What it validates:
   - Email syntax follows RFC 5322 (the global email standard).
   - The local part (before `@`) and the domain contain only valid characters.
   - The `@` is placed correctly and the domain is structured correctly.

- What it transforms:
   - Converts all emails to lowercase (`User@Example.com` → `user@example.com`).

- Why it matters:
   - Prevents duplicate profiles when the same user signs up with different casing.
   - Stops invalid emails from causing hard bounces at send time.
   - Reduces rejections from email service providers.

- Example: 

| Incoming data | Result | Reason |
| :--- | :--- | :--- |
| `user@example.com` | Stored as `user@example.com` | Valid |
| `User@Example.com` | Stored as `user@example.com` | Valid, converted to lowercase |
| `user.name@example.com` | Stored as `user.name@example.com` | Valid |
| `user..name@example.com` | Dropped | Invalid (consecutive periods) |
| `userexample.com` | Dropped | Invalid (missing `@`) |
| `user@` | Dropped | Invalid (missing domain) |

##### Mobile number

The Mobile number rule makes sure numbers comply with the E.164 global standard for phone numbers.

- What it validates: 
   - The number has a `+` prefix.
   - The country code is valid (1–3 digits).
   - The subscriber number is valid (up to 12 digits).
   - The total length is 15 digits or fewer.
   - The number contains no special characters (spaces, hyphens, or parentheses).

- Why it matters: 
   - E.164 is required by the WhatsApp Business API and SMS aggregators (such as Twilio and Vonage).
   - It prevents ambiguity across different countries.
   - It stops messages from failing due to routing errors.

- Example:

| Incoming data | Result | Reason |
| :--- | :--- | :--- |
| `+14155552671` | Stored | Valid E.164 |
| `+919876543210` | Stored | Valid E.164 (India) |
| `+447123456789` | Stored | Valid E.164 (UK) |
| `14155552671` | Dropped | Invalid (missing `+` prefix) |
| `+1 (415) 555-2671` | Dropped | Invalid (contains spaces and parentheses) |
| `(0) 98765 43210` | Dropped | Invalid (not in E.164 format) |

<Tip>
  Before you enable the Mobile number rule, make sure your data source sends numbers in E.164 format. If your existing data uses local formats (such as `(0) 98765 43210`), update your ingestion pipeline to transform it first.
</Tip>

#### FAQs on Rules

<AccordionGroup>
  <Accordion title="Why am I unable to apply rules?">
   You can apply validation rules only to an attribute whose allowed data type is **String** and that doesn't have PII encryption enabled.
  </Accordion>
  <Accordion title="How do the rules work with PII encryption?">
    Validation rules can't validate encrypted data because the values appear as encrypted strings. If you use PII encryption, you must disable validation rules.
  </Accordion>
  <Accordion title="What happens if I disable a rule?">
    Validation stops immediately. Existing records are not affected, and new incoming data is no longer validated.
  </Accordion>
  <Accordion title="Can I validate data after it's already in MoEngage?">
    No. Validation rules apply only to incoming data. To validate existing user records, export the attribute, clean it externally, and re-import it.
  </Accordion>
</AccordionGroup>

### Array Typecasting

All the elements in the array have to be homogenous, which means they must be either integers or strings. If they are not homogenous, MoEngage tries to typecast (transform) the element and then store the data. Following is the example of an array in a CSV field: \[1|2|3\] <img src="/images/moengage_c53a6c.png" />

If an array has elements \[1 | 2 | “abc”\] which has multiple datatypes and the defined datatype is Array Integer based on the first element, then the array or the entire datapoint will not be ingested as "abc" cannot be successfully typecasted into Integer.

Empty arrays \[\] ingestion is supported and will unset the existing array attribute.
