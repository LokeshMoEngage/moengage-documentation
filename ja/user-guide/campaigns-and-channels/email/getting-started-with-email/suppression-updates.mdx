# 概要

_Suppression Updates_ は、グローバルな Eメール購読リストの維持に役立ちます。この機能を使用すると、連絡すべきでないユーザーが Eメールを受信しないように制限できます。これは、コンプライアンスを維持し、送信者レピュテーションを保護するために不可欠です。

抑制によってブロックされるのは、プロモーションキャンペーンとマーケティングキャンペーンのみです。トランザクションとしてタグ付けされたキャンペーン (配信チャネルから送信されたもの、または Inform 経由で送信されたもの) は、抑制されたユーザーにも届きます。唯一の例外はバウンスで、トランザクションを含むすべてのキャンペーンタイプがブロックされます。

<Info>
  MoEngage Managed Email を使用している場合、到達可能性の更新は SendGrid に自動的に反映されます。ただし、独自の SendGrid アカウントを統合している場合、この自動同期はサポートされないため、SendGrid ダッシュボード内で抑制の更新を直接管理する必要があります。
</Info>

# 配信停止と抑制の違い

配信停止と抑制は関連していますが、異なる概念です。この 2 つを混同すると、抑制管理が正しく行われず、コンプライアンス上のリスクにつながる可能性があります。

**配信停止 (Unsubscribe)** はユーザーのアクションです。ユーザーが配信を停止すると、MoEngage はそのプロファイルの標準の配信停止属性を `True` に設定します。これは、ユーザーが抑制される複数の理由の 1 つです。

**抑制 (Suppression)** はプラットフォーム側の結果です。MoEngage は、ユーザーのプロファイルについて次のいずれかに該当する場合、そのユーザーを抑制します (つまり、トランザクション以外のキャンペーンの送信を停止します)。

- BUC 属性 (Bounce、Unsubscribe、または Complaint) のいずれかが `True` に設定されている
- Frequency Capping (FC) の上限に達している
- Do Not Disturb (DND) 設定が適用される
- ユーザーが購読カテゴリをオプトアウトしている
- Double Opt-In (DOI) が未確認である

| 観点 | 配信停止 | 抑制 |
|---|---|---|
| **トリガー** | ユーザーのアクション — ユーザーが配信停止をクリックし、プロファイルの Unsubscribe 属性 (3 つの BUC 属性の 1 つ) が `True` に設定される | プラットフォームのアクション — BUC 属性、FC、DND、購読カテゴリ、または DOI のいずれかの条件が満たされたときに発生する |
| **範囲** | ユーザープロファイルに属性を設定する | プロモーション/マーケティングキャンペーンのみをブロックする。トランザクションとしてタグ付けされたキャンペーン、または Inform 経由で送信されたキャンペーンはユーザーに届く。唯一の例外はバウンスで、トランザクションを含むすべてのキャンペーンタイプをブロックする |
| **可逆性** | 可逆 — 再購読フローによって属性をリセットできる | トリガーによっては可逆だが、抑制条件を解除しても明示的な同意は回復しない (以下のコンプライアンスに関する注記を参照) |
| **管理者** | エンドユーザーが直接管理する | プロファイル属性に基づいて MoEngage が管理する。ブランドは以下の方法でこれらの属性に影響を与えることができる |

## ブランドが抑制を管理する方法

MoEngage Eメールには単一の "抑制リスト" はありません。抑制はユーザーのプロファイル上の属性によって決定され、ブランドは次の 2 つの方法でこれらの属性を更新できます。

1. **データエコシステムによる更新** — User Import または Server-to-Server (S2S) Data API。これらは関連する標準属性を直接上書きしますが、イベントは生成しません。(例外: ダッシュボードのユーザーのプロファイルページから行った更新は Eメール API を経由するため、イベントが生成されます。)
2. **Eメールベースの更新** — Eメール設定の Suppression Management セクション、または Resubscribe API、Subscription Category API、Double Opt-In API。これらは対応する標準属性を更新し、ユーザーのプロファイルに対してイベントを生成するため、同意の変更を追跡可能な記録として残すことができます。

同意の変更の監査証跡が必要な場合は、Eメールベースの方法を使用してください。

<Note>
  抑制は抑制リストと同じではありません。MoEngage Eメールはネイティブには抑制リストを保持しません。これは送信リクエストごとに MoEngage 側で行われる判断です。プロモーションキャンペーンの場合、ユーザーがバウンス、苦情、または配信停止の状態であれば、MoEngage は送信を抑制し、リクエストを送信者に転送しません。トランザクションキャンペーンの場合、MoEngage が送信を抑制するのはユーザーがバウンスの状態である場合のみです。苦情または配信停止の場合、MoEngage は引き続き送信リクエストを送信者 (たとえば SendGrid) に送信します。
</Note>

# ユースケース

- **従来の Eメールマーケティングプラットフォームまたは ESP からの移行**: MoEngage に移行する際に、過去の抑制リスト (バウンス/配信停止/スパム) を一括インポートして、初日から送信者レピュテーションを保護します。
- **SendGrid 同期の自動化:** 抑制の更新を SendGrid に自動的に反映し、手作業なしでトランザクション以外の送信者のコンプライアンスを維持します。これは、MoEngage で Eメール送信者を構成する際に **Unsubscribe Settings** で [**SendGrid Tracking**](/ja/partner-guide/messaging-channels/email-providers/configure-sendgrid#configure-unsubscribe-settings-and-list-unsubscribe-email) を選択した場合にのみ適用されます。
- \*\*重要な Eメールの保護: \*\*ワンタイムパスワード (OTP) やパスワードリセットなどの重要なトランザクションアラートをブロックすることなく、マーケティングキャンペーン用のグローバル抑制リストを維持します。
- **抑制リクエストの独立した管理**: [セルフサービス](/ja/user-guide/campaigns-and-channels/email/getting-started-with-email/self-service-for-email-onboarding)が有効なワークスペースでユーザーの配信停止または再購読を行い、個々のステータス更新のためにサポートチケットを発行する必要をなくします。

# ユーザーの一括インポート

_Suppression Updates_ の主な機能は、既存の購読リストを一括でインポートすることです。これは、特に以前の Eメールマーケティングプラットフォームまたは ESP から移行する場合に、Eメールオンボーディング中の重要な手順です。

この機能を使用して、過去に次のような状態になったユーザーの CSV リストをアップロードします。

- Eメールがバウンスした。
- コミュニケーションの配信を停止した。
- Eメールをスパムとしてマークした (苦情)。

## CSV ファイルの要件

購読リストが正しくインポートされるよう、CSV ファイルは次の要件に従う必要があります。

- CSV ファイルは、以下に示す列の順序に厳密に従う必要があります。列ヘッダーの大文字と小文字は区別されませんが、正常に処理されるよう順序を変更しないでください。
  - 識別子列: この列には _Email ID_、_MoEngage ID,_、または _Email ID/MoEngage ID_ というラベルを付けます。ワークスペースで PII トークン化が有効になっている場合は、この列に _ID_ というラベルを付ける必要があることに注意してください。
  - _Unsubscribe_
  - _Bounce_
  - _Spam_
- 各ユーザーについて、CSV では Unsubscribe、Bounce、Spam の列に _true_ または _false_ (大文字と小文字は区別されません) を指定する必要があります。たとえば、配信を停止したものの、バウンスしたこともスパムとしてマークしたこともないユーザーの値は次のようになります。
  - _Unsubscribe_: true
  - _Bounce_: false
  - _Spam_: false
- CSV ファイルに重複する Eメールエントリを含めないでください。重複が見つかった場合、MoEngage はファイル内の最後のエントリのみを処理し、それより前の重複はすべてスキップします。 
- ユーザーが再購読したとみなされるのは、MoEngage が 3 つの抑制カテゴリすべてについて、ステータスを true (抑制) から false (アクティブ) に更新した場合のみです。3 つのエントリすべてについてユーザーの現在のステータスがすでに false の場合、更新は行われません。
- 3 つの抑制カテゴリすべてが false に設定されている場合、ユーザーは到達可能になり、3 つのカテゴリのいずれかが true に設定されている場合、ユーザーは抑制されます。
- _Unsubscribe_ 列に指定した値に応じて、同じ CSV ファイルを使用してユーザーの配信停止または再購読を行うことができます。以前に配信を停止したユーザーを到達可能にするには、_Unsubscribe_ の値を _false_ に設定したファイルをアップロードします。_Bounce_ と _Complaint_ も _false_ であれば、そのユーザーは再び Eメールを受信できるようになります。
- BUC 属性 (Bounce、Unsubscribe、または Complaint) のステータスが変更されると、MoEngage は次のイベントを生成します。

<Warning>
  抑制条件を解除しても (たとえば、以前に配信を停止したユーザーを一括インポートで再追加しても)、そのユーザーの同意は回復しません。抑制と同意は別々に追跡されます。抑制フラグをクリアしても、ユーザーが再び送信対象になるだけであり、再度オプトインしたことを意味するわけではありません。以前に抑制または配信停止されたユーザーへの送信を再開する前に、有効な同意があることを確認してください。
</Warning>

## 購読更新ファイルをアップロードする

- ワークスペースで Eメールオンボーディングのセルフサービスが有効になっている場合は、[こちら](/ja/user-guide/campaigns-and-channels/email/getting-started-with-email/self-service-for-email-onboarding#manage-email-suppression)の説明に従って抑制を管理できます。
- ワークスペースで Eメールオンボーディングのセルフサービスが有効になっていない場合は、[こちら](/ja/user-guide/campaigns-and-channels/email/getting-started-with-email/configure-email-channel#subscription-management-tab)の説明に従って抑制を管理できます。 

# FUP の制限

システムの安定性を維持し、Suppression Management サービスへの過剰な負荷を防ぐため、ワークスペースレベルで次の制約が適用されます。

- **ファイルサイズの上限**: アップロードは 1 ファイルあたり 75 MB に厳密に制限されています。
- **重複ファイル名の検証**: 冗長な処理を避けるため、MoEngage は既存のファイル名をチェックします。同じ名前のファイルがすでに処理されている場合、アップロードリクエストは拒否されます。
- **アップロード頻度の制限**: リソースを公平に利用できるよう、ファイルのアップロードには次の頻度制限が適用されます。
 
  | 時間枠 | 許可される最大アップロード数 |
  | :--- | :--- |
  | 5 分 | 5 回 |
  | 15 分 | 10 回 |
  | 1 時間 | 20 回 |
  | 24 時間 | 50 回 |

  <Accordion title="別の ESP から MoEngage に移行する際、バウンス、配信停止、苦情 (BUC) をどのように管理すればよいですか？">
    以前の ESP から MoEngage に移行する場合は、Subscription Management 内の一括インポート機能を使用する必要があります。以前のプロバイダーから既存の抑制リスト (バウンス、配信停止、または苦情のあったユーザー) をエクスポートし、CSV ファイルとして MoEngage にアップロードします。これにより、MoEngage が過去のデータを尊重し、これらのユーザーが Eメールを受信しないよう恒久的に制限するため、初日からレピュテーションを保護できます。
  </Accordion>

  <Accordion title="以前の購読リストをインポートすることが重要なのはなぜですか？">
    リストのインポートは、コンプライアンスの維持 (以前のオプトアウトの尊重) と送信者レピュテーションの保護に不可欠です。過去にバウンスしたユーザーやスパムとしてマークしたユーザーに Eメールを送信すると、配信到達性が大きく損なわれ、ISP が今後の Eメールをブロックする原因となる可能性があります。
  </Accordion>

  <Accordion title="この機能を使用して、ユーザーグループへの Eメールを一時的に停止できますか？">
    いいえ。Subscription Management は、恒久的な制限 (法的なオプトアウトやハードバウンスなど) を目的として設計されています。グループ (例: "Unengaged Users") を一時的に除外したい場合は、グローバルな BUC ステータスを変更するのではなく、特定のセグメント (抑制リスト) を作成し、キャンペーンの作成時にそれを除外してください。
  </Accordion>

  <Accordion title="抑制リストはトランザクション Eメール (パスワードリセットや OTP など) をブロックしますか？">
    キャンペーンが "transactional" タイプとしてタグ付けされている場合、または inform アラートが送信される場合、抑制リストは配信停止/苦情フラグを無視します。ただし、ユーザーがバウンスとしてマークされている場合、Eメールは送信されません。
  </Accordion>

  <Accordion title="一括インポートファイルを使用してユーザーを再購読させることはできますか？">
    はい。属性値を false に設定することで、ユーザーを再び到達可能にできます。これらのいずれかが true に設定されている場合、ユーザーは "抑制" されているとみなされます。
    再購読させるには、そのユーザーの **Bounce**、**Unsubscribe**、**Complaint** の列がすべて false に設定された CSV をアップロードします。
    <Warning>
     **ユーザーの再購読に関するコンプライアンスの注記:** 抑制リストからユーザーを削除しても (Unsubscribe を false に設定しても)、解除されるのは MoEngage の送信ブロックのみであり、同意は回復しません。以前に配信を停止したユーザーへのマーケティング Eメールを再開する前に、適用される規制 (CAN-SPAM、GDPR、CCPA など) で求められる有効かつ最新の同意があることを確認してください。新たな同意なしにユーザーを再追加すると、MoEngage が技術的には Eメールを配信するとしても、コンプライアンス違反となる可能性があります。
    </Warning>
  </Accordion>

  <Accordion title="CSV ファイルのセルを空白 (空) のままにするとどうなりますか？">
    セルが空の場合、MoEngage はそのユーザーの特定の属性を変更しません。属性は、ユーザーのプロファイルに現在存在する値をそのまま保持します。
  </Accordion>

  <Accordion title="一括インポート中に、MoEngage はどのように更新対象のユーザープロファイルを特定しますか？">
    MoEngage は、CSV ファイル内の Eメールアドレスを、Email General Settings で構成されたユーザー属性と照合してユーザーを特定します。
    具体的には、MoEngage は **User attribute that stores the email address** フィールドで定義された属性を参照し、アップロードされた CSV 内のすべての Eメール ID をユーザーベース全体のこの属性と比較します。その属性に一致する Eメールアドレスを含むユーザープロファイルはすべて更新されます。
  </Accordion>

  <Accordion title="ユーザーの配信停止または再購読を行う際に、同じ Eメールアドレスを持つプロファイルが複数ある場合はどうなりますか？">
    "Unsubscribe based on email ID" 機能が設定されている場合、その Eメールアドレスに関連付けられているすべてのユーザープロファイルが、それに応じて配信停止または再購読されます。
  </Accordion>

  <Accordion title="Suppression Management で行われた変更を監査するにはどうすればよいですか？">
    完全なトレーサビリティを確保するため、すべての変更は [Audit Logs](/ja/user-guide/settings/account/audit-logs/audit-logs#email-suppression-updates) に自動的に記録されます。
  </Accordion>
</AccordionGroup>
