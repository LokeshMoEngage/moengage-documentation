# 概要

多くの場合、ユーザーのプロパティやイベントとして記録された過去のアクションに基づいて、個々のユーザーごとに異なるカスタマイズされたチェックを作成する必要があります。Linked Conditions（リンク条件）を使用すると、フローに追加してユーザーのパスを決定する、このような条件チェックを実現できます。これにより、マーケターは固定値を指定する代わりに、ユーザー属性、アクション、ジャーニーの進行状況に基づいたインテリジェントなチェックを考案できます。

たとえば、リンク条件を使用して、ユーザーが商品を少なくとも 1 回カートに追加したもののまだ購入していないか、または閲覧していたのと同じブランドの商品を購入したかを確認できます。フローのエントリー条件にチェックを追加して、ユーザーが以前カートに追加した特定のカテゴリの商品または特定の商品を購入したかどうかを、手動で指定することなく評価できます。

e コマースプラットフォームで靴を閲覧しているユーザー John を考えてみましょう。John はブローグシューズをカートに追加します。カートへの追加イベントを実行したため、John はフロー F1 の評価対象となります。

フロー内でリンク条件チェックがどのように機能するかを以下に示します。

John が Add to Cart イベントを実行した場合:

- Add to Cart イベントから 2 時間後に Product Purchase イベントを実行していないかを確認します
- カートに追加された商品の product id と、商品購入イベントの product id を照合します

![Dynamic condition FLOWS\_updated.png](/images/moengage_907ad1.png)

商品購入に対するチェックは静的な値に紐づくのではなく、親イベント（この場合はカートへの追加イベント）に対して動的にチェックされるため、リンク条件を使用すると、上記のようなフローを複数の商品や商品カテゴリに使用できます。動的チェックを使用して、フライトのチケットを購入したユーザーにフライト遅延に関するカスタマイズされたコミュニケーションを送信したり、支払期限が近づいているアカウント内の特定のカードの請求をまだ支払っていない顧客に支払いリマインダーを送信したりできます。

<Note>
  トリガーフローで Linked Conditions が有効な場合、各ユーザーが同時に持てる進行中のエントリー評価は最大 **10 件**です。この制限を超えて新しい評価が開始されると、MoEngage はそのユーザーの最も古い進行中の評価を置き換えます。
</Note>

## ユースケース

特定の目的で Linked Conditions を活用する例をいくつか紹介します。

- **2 つのイベント間のワイルドカードチェック -** これは、特定のイベントが発生し、他のイベントが発生していない場合にのみユーザーをフローに入れるための効果的なアプローチです。ある組織が、クレジットカードを持ち、請求明細を受け取り、1 枚以上のカードの請求を支払っていない顧客にリマインダー通知を送信するルールを作成したい場合を考えてみましょう。ここでリンク条件のアプローチが役立ちます。銀行のクレジットカードアカウントを持つユーザーが請求を支払っていない場合に対象となるフローを考えます。次の条件チェックを追加します。
  - ユーザーに請求書発行イベントがあるか?
  - ユーザーに支払い済みイベントがあるか?
  - Payment Bill.Card\_ID = Bill Generated.Card\_ID を動的に比較して、請求書発行イベントと支払い完了イベントを比較します 
  
この条件を満たすユーザーを、支払いリマインダーキャンペーンを送信するフローに入れます。その他のユーザーはフローから除外します。このような設定では、請求明細発行のトリガーイベントを捕捉し、指定した期間、請求の支払いを示すユーザーアクションが発生するのを待ちます。ユーザーアカウント内のいずれかのカードについてこのアクションが行われなかった場合、その特定のカードの請求を支払うようユーザーにリマインダー通知を送信します。このアプローチにより、システム内の特定のユーザー行動に対応する、カスタマイズ可能で自動化された方法が提供されます。
- **同じ属性で同じ親イベントを X 回繰り返す -** これは、商品を複数回検索するなど、特定のアクションを完了したユーザーをフローに入れるために使用できる手法です。たとえば、e コマースプラットフォームが、顧客が以前の検索の続きから始められるパーソナライズされたユーザーエクスペリエンスを作成したい場合に、このアプローチを効果的に使用できます。次のリンク条件があるフローを考えます: ユーザーはフロー内にいる間に、指定期間内にキーワードまたは商品を複数回検索したか、そしてユーザーはアクティブなセッションを持っているか、または頻繁に購入するユーザーか?\
  該当する場合、検索履歴に基づいて類似商品、お得情報、プロモーションを提案するキャンペーンが送信されるフロー内のパスにユーザーを進めます。

# メリット

1. 購買意欲の高いユーザーにアプローチし、BTS や MPC などの他の強力な機能を使用して最適な方法でエンゲージメントを図ることができます。
2. この機能の柔軟性により、エントリーステージ、条件ステージ、またはその両方でユーザーを評価することを選択できます。
3. ルールを簡単に定義し、購買意欲の高いユーザーを見つけることができます。
4. フローでユーザーをターゲットにするための条件/ルールの定義において、より高い柔軟性が得られます。
5. ユースケースを実現するために必要なフローの数が少なくて済みます

# Linked Conditions の追加

Linked Conditions は、フローの次のセクションに追加できます。

<Tabs>
  <Tab title="エントリー条件">
    今後のフライトに関する通知やリマインダーを送信するフローを考えてみましょう。これを実現するために、エントリーレベルで次のチェックを追加できます。

    1. ユーザーは、今後の旅行日があるいずれかのフライトのチケットを購入したか?
    2. ユーザーがチケットをキャンセルしていないことを確認します。
    3. また、エントリーのきっかけとなった旅行のチケットをキャンセルしたエントリー済みユーザーを削除することもできます。

    このような情報をユーザーに伝える際に、チケットのアップグレードを促したり、他のサービスをクロスセルしたりするキャンペーンを送信することもできます。

    ![Global Exit Criteria.gif](/images/moengage_8e6162.png)

    **注**: フローはユーザーの進行状況を追跡し、指定された条件が満たされたときに特定のアクションを開始できますが、一度に対応できるのはユーザーの単一インスタンスのみです。ユーザーがリンク条件を複数回満たすことが予想され、そのすべてのインスタンスに対してメッセージを送信したい場合、MoEngage はイベントトリガーキャンペーンでリンクトリガーを使用することを推奨します。

    同じフローで、エントリー済みユーザーがフライトチケットをキャンセルした時点でフローから退出させることができます。
  </Tab>
  <Tab title="Has Done ステージ">
    このセクションで説明した、ユーザーが商品をカートに追加したもののまだ購入していない例を考えてみましょう。以下に示すように、フローに Has Done 条件ステージを追加してこれを動的にチェックし、カートに追加した商品を購入していないユーザー向けにコミュニケーションをパーソナライズし、それ以外のユーザーを退出させることができます。

    ![DynamicConditions\_HasDone.gif](/images/moengage_8f1f60.png)
  </Tab>
  <Tab title="Conditional Split ステージ">
    購買意欲の高いユーザーをさまざまなキャンペーン戦略で分類するフローを考えてみましょう。

    1. 同じ商品を 5 回以上閲覧したユーザーには、商品購入のためのインセンティブ（20% オフ）を提供します
    2. 1 回より多く閲覧したユーザーには、まずナッジを送り、その後商品購入のためのインセンティブ（10%）を提供します
    3. 1 回閲覧したユーザーには、ナッジと類似商品のレコメンデーションを送ります。<img src="/images/moengage_e4ab06.png" alt="DynamicConditions_ConditionalSplit.gif" />
  </Tab>
</Tabs>

Linked Conditions のさまざまな用途を確認したら、[Flows - クロスチャネルメッセージングのセクション](/ja/user-guide/flows-cross-channel-messaging)に移動して、Flows の機能について確認し、フローを作成してください。
