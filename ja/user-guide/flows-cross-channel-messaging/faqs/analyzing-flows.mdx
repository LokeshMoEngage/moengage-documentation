# 指標、ドロップオフ、失敗の理由

### Flows ではどのような指標や統計が追跡されますか？

公開済み Flow では、キャンバスの上部に Flow の指標が表示されます。各指標の詳細については、[Flow Stats](/ja/user-guide/flows-cross-channel-messaging/analyze-flows/analyze-a-flow) を参照してください。

### ドロップオフとは何ですか？

ドロップオフは、フロー内でユーザートリップが途中で突然終了した場合に発生します。これにはさまざまな理由があり、たとえば次のようなものがあります。

1. フリークエンシーキャップ (FC) の上限に達しており、メッセージが送信されなかった場合にユーザーをフローから削除するよう Flow が設定されている場合。
2. Do Not Disturb 設定によりメッセージが配信されず、メッセージが配信されなかった場合にユーザーを Flow から削除するよう Flow が設定されている場合。
3. 一時停止中のフローを再開した場合、または待機期間がすでに終了している状態でユーザーが Wait For/till ステージに入った場合。
4. 既知のユーザーが別のユーザーとマージされた後、すでに同じフローに参加している場合。
5. Flow の実行中に何らかの内部エラーが発生した場合。

### ドロップオフと Exit の違いは何ですか？

ドロップオフは、マーケターが制御できない理由でフロー内のユーザートリップが途中で突然終了した場合に発生します。一方、Exit は [Exit Conditions](/ja/user-guide/flows-cross-channel-messaging/create/create-flows/create-a-flow) などの定義済みの条件によってユーザートリップが終了した場合に発生します。

### 送信されなかったキャンペーンの失敗理由はどこで確認できますか？

各チャネルのパフォーマンスが低い理由を特定するには、Flows の **Stats** タブにある **Channel Performance** セクションに移動します。キャンペーンレベルのインサイトについては、キャンバス内のキャンペーンステージにカーソルを合わせると表示される **i** アイコンをクリックするか、Flows の **Stats** タブにある **Campaign Performance** セクションでキャンペーン名をクリックして、**Campaign Info** ページにアクセスします。

### なぜユニーク数ではなくトリップを使用するのですか？

トリップは、ユーザーがライフタイムを通じてフローに入る各インスタンスを一意に識別することで、フローの指標を曖昧さなく追跡・分析する方法を提供します。ユーザーの総エントリー数も監視できますが、指標の曖昧さを取り除き正確なレポートを提供するためには、ユニークユーザーエントリー数やユニークコンバージョン数などの補助的な指標を追跡する必要があります。そのため、フローのパフォーマンスを理解するにはトリップの方が適切で有用です。

## 条件ステージ

### Flows 内の Condition ステージでは、ユーザーはどのように評価されますか？

ユーザーが条件ステージに入ると、定義された期間に基づいて評価されます。この評価期間中にユーザーが条件を満たすと、すぐに "Yes Path" に進みます。"Keep Evaluating for" の期間は評価に許容される最大時間であり、動的です。そのため、評価期間全体を通じてイベントを実行しなかったユーザーは、期間の終了時に "No Path" にリダイレクトされます。

**注**: この動的な評価により、コミュニケーションのタイミングが改善され、より適切なコンテキストが提供されます。

### Flows 内の Condition Split ステージでは、ユーザーはどのように評価されますか？

ユーザーは、定義された評価期間全体にわたって、最初のブランチで定義された条件について評価されます。要件を満たした場合は Branch 1 に進みます。ただし、要件を満たさない場合は、評価期間全体を待機し、その期間中のいずれかの時点で同じユーザーが Branch 1 の条件を満たすかどうかを確認します。

評価期間の終了後、ユーザーが条件を満たすその他すべてのブランチのパスを検討します。条件ブランチには優先順位の階層があり、Branch 1 の優先度が最も高く、デフォルトブランチの優先度が最も低いため、この優先順位付けが必要です。

## コントロールグループとアップリフト

### コントロールグループのアップリフトはどのように機能しますか？

アップリフトは、コントロールグループのユーザーを分析することで、オーガニックな行動と比較したパフォーマンスを評価できる指標です。コンバージョンアップリフトは、ターゲットグループのコンバージョンとコントロールグループのコンバージョンの差の割合を表します。詳細については、[Flows におけるコントロールグループ](/ja/user-guide/flows-cross-channel-messaging/create/experimentation/control-group-in-flows)を参照してください。

### コントロールグループとターゲットグループの両方のユーザーについて、コンバージョンはどのようにアトリビューションされますか？

コンバージョンしたユーザーのトリップとは、Flows のコミュニケーションに直前にエンゲージした後、定義されたアトリビューション期間内に指定された目標に到達したユーザーのトリップを指します。コントロールグループ (CG) のユーザーはコミュニケーションを受信しないため、デフォルトでエンゲージ済みと見なされます。コンバージョンの基準は両方のタイプのユーザーに適用され、これらの条件を満たさないユーザーは Flows にアトリビューションされません。

コンバージョンしたユニークユーザーを特定するには、セグメンテーションで Flow ID を属性として Has Executed Flow Trip Conversion をクエリします。詳細については、[Flows におけるコンバージョンアトリビューション](/ja/user-guide/flows-cross-channel-messaging/analyze-flows/conversion-attribution-in-flows)を参照してください。

### アップリフト指標が表示されないのはなぜですか？

CVR のアップリフト指標は、コントロールグループ (CG) のトリップが発生してから少なくとも 24 時間が経過した場合にのみ表示されます。

### アップリフトがマイナスの場合はどうすればよいですか？

コントロールグループ (CG) のユーザーがターゲットユーザーよりも多くコンバージョンしている場合、アップリフト指標はマイナスになります。この状況を改善するには、A/B Split ステージやキャンペーン内のバリエーションを使用してコミュニケーションのコンテンツを試してください。また、パフォーマンスの高いチャネルをフローの上位に配置して優先することも効果的です。

さらに、Flows で NBA を使用してメッセージ配信のタイミングを試すことで、ユーザーをコンバージョンさせる可能性を高めることができます。NBA は、各ユーザーの好みのチャネルとコミュニケーションを送信する最適な時間を特定するためです。

### フローに入ったユーザーとコンバージョンしたユーザーの中から、コントロールグループのユーザーを見つけるにはどうすればよいですか？

コントロールグループに属するユーザーを見つけるには、"User Entered Flow" オプションを使用してセグメント化し、"Flow ID" 属性と "With Control Group" 属性でフィルタリングします。詳細については、[Flow のコントロールグループユーザー](/ja/user-guide/flows-cross-channel-messaging/create/experimentation/control-group-in-flows)を参照してください。

コントロールグループのうちコンバージョンしたユーザーを特定するには、"Flow Trip Conversion" を使用してセグメント化し、"Flow ID" 属性と "User Type" 属性でフィルタリングします。詳細については、[Flow のコンバージョンしたユーザーの追跡](/ja/user-guide/flows-cross-channel-messaging/analyze-flows/conversion-attribution-in-flows)を参照してください。

# 低い統計値

### Total Trips 指標が低いのはなぜですか？

ユーザーがフローに入るには、定義されたターゲットオーディエンスセグメントに属し、エントリー制限 (Flow で指定されている場合) などのその他の条件を満たした状態で、トリガーイベントを実行する必要があります。また、エントリーの検討時点で、ユーザーがその Flow のアクティブなトリップに参加していない必要があります。

ターゲットオーディエンスがイベントベースまたはカスタムセグメントベースのチェックで定義されている場合、セグメントは 3 時間ごとに 1 回更新されます。そのため、新たに追加されたユーザーは、トリガー条件を再度満たした場合にのみ Flow に再エントリーします。

Total Trips 指標が低すぎると思われる場合は、ターゲットオーディエンスの定義にイベントベースまたはカスタムセグメントベースのチェックを使用しないことを検討してください。ユーザーを取りこぼさないよう、これらのチェックは Entry ステージの後の最初のステップとして Flow 内に組み込んでください。

### Conversion 指標が低いのはなぜですか？

Conversion 指標が低い場合、コンバージョンしたトリップ数が、追跡しているイベントを実行したユーザー数よりも少ない可能性があります。Flows から送信されたいずれかのコミュニケーションにエンゲージした後、アトリビューション期間内にイベントを実行したユーザーのみがコンバージョンとしてカウントされます。

一度もエンゲージせずに目標イベントを実行したユーザーや、エンゲージ後にアトリビューション期間外で目標イベントを実行したユーザーは考慮されません。そのため、これらのユーザーはコンバージョン数に含まれず、指標が低下する原因となる場合があります。

### Total Trips 指標がゼロなのはなぜですか？

フローがエントリーの受け付けを開始するまでに許容される最大時間は、ターゲットオーディエンスの定義によって異なります。

- ターゲットオーディエンスが "All users" またはユーザープロパティのチェックで定義されている場合、最大時間は 10 分です。
- ターゲットオーディエンスがその他のチェックで定義されている場合、最大時間は 60 分で、セグメントは 60 分以内に更新されます。含まれなかったユーザーは 3 時間後に参加します。

したがって、公開からの経過時間がこれらの SLA の範囲内であれば、フローがエントリーを処理するまでお待ちください。期限を過ぎている場合は、Visualize user trip 機能を使用して、対象ユーザーがエントリーしていない理由を特定してください。詳細については、[ユーザートリップの可視化](/ja/user-guide/flows-cross-channel-messaging/analyze-flows/debug-flows)を参照してください。

## Flows 内の統計、およびセグメンテーションと Flows の間での数値の違い

### Unique Conversions の合計が Converted Trips や Conversions と異なるのはなぜですか？

Converted Trip とは、フローからのコミュニケーションにエンゲージし、定義されたアトリビューション期間内にコンバージョン目標イベントを実行したユニークなユーザートリップです。ただし、この指標はフローレベルでのみユニークです。たとえば、ユーザー (A) が 1 回のトリップで 2 回コンバージョンした場合、Converted Trip は 1 ですが、Conversions は 2 になります。詳細については、[コンバージョンアトリビューション](/ja/user-guide/campaigns-and-channels/campaign-management-and-reports/conversion-and-attribution)を参照してください。

アトリビューションに重複が生じるため、キャンペーンステージに表示されるコンバージョン数を合計してフローレベルの数値と一致させることはできません。たとえば、2 つの Push ステージ PN1 と PN2 があり、その間に 2 時間の _Wait Till_ ステージがあるフローを考えてみます。この Flow のアトリビューション期間は 36 時間です。

John は次のようなユーザーです。

- 午前 11 時 30 分にフローに入る
- 午後 12 時に PN1 にエンゲージする
- PN2 にはエンゲージしない
- 午後 8 時にコンバージョンする

![Flows\_FAQs.png](/images/moengage_6448a8.png)

このシナリオのコンバージョン指標は次のとおりです。

| 指標 | レベル (Flow/Campaign) | カウント |
| --- | --- | --- |
| Converted Trips | Flow | 1 |
| Conversions | Flow | 1 |
| Conversions | Push Campaign PN1 | 1 |
| Conversion Events | Push Campaign PN1 | 1 |
| Conversions | Push Campaign PN2 | 0 (John は PN2 にエンゲージしていない) |
| Conversion Events | Push Campaign PN2 | 0 (John は PN2 にエンゲージしていない) |

Jane は次のようなユーザーです。

- 午前 11 時 45 分にフローに入る
- PN1 を受信し、午後 12 時にエンゲージする
- PN1 を受信し、午後 3 時にエンゲージする
- 午後 9 時にコンバージョンする

![Flows\_FAQs1.png](/images/moengage_fd1b5e.png)

John と Jane の両方がフローに参加しているこのシナリオのコンバージョン指標は次のとおりです。

| 指標 | レベル (Flow/Campaign) | カウント |
| --- | --- | --- |
| Converted Trips | Flow | 2 (John と Jane でそれぞれ 1) |
| Conversions | Flow | 2 (John と Jane でそれぞれ 1) |
| Conversions | Push Campaign PN1 | 2 (PN1 と PN2 の両方のアトリビューション期間内にコンバージョンが行われたため、John と Jane でそれぞれ 1) |
| Conversion Events | Push Campaign PN1 | 2 (PN1 と PN2 の両方のアトリビューション期間内にコンバージョンが行われたため、John と Jane でそれぞれ 1) |
| Conversions | Push Campaign PN2 | 1 (Jane は PN2 にエンゲージしたが John はエンゲージしなかったため、PN2 でコンバージョンしたのは Jane のみ) |
| Conversion Events | Push Campaign PN2 | 1 (Jane は PN2 にエンゲージしたが John はエンゲージしなかったため、PN2 でコンバージョンしたのは Jane のみ) |

Jane のアトリビューションが重複しているため、PN1 と PN2 の Conversions の合計は Converted Trips よりも大きくなります。

### Converted trips の統計が、目標イベントを確認する _Has Done Event_ で Yes パスを通過したユーザー数と一致しないのはなぜですか？

Flow から送信されたコミュニケーションを操作した後、アトリビューション期間内にイベントを実行したユーザーのみが Converted trips としてカウントされます。そのため、Converted trips の数はイベントを実行したユーザー数よりも少なくなります。

**Has Done** イベントやその他の条件ステージは、エンゲージ状況ではなく、評価期間全体を通じて条件が満たされているかどうかを確認します。この評価基準の違いが、数値が異なる場合がある理由です。

### セグメンテーションやファネルの数値が Flow の統計の数値と異なるのはなぜですか？

Flows の統計はユニークトリップレベルで指標の数値を表示しますが、セグメンテーションはユニークユーザーレベルで数値を表示します。そのため、同じユーザーがフローに 2 回入った場合、Flows の Total Trips は 2 と表示されますが、同じフローについてセグメンテーションで "_User Entered Flow_ をクエリすると値は 1 と表示されます。

また、Flows ではアトリビューションロジックが異なるため、ファネルと Flows の数値 (特に Conversions) を比較することはお勧めしません。Flows では、ユーザーがエンゲージメントを示すたびにアトリビューション期間が延長されます。一方、ファネルでは入力したアトリビューション期間は固定されているため、終了時刻が定まっています。

そのため、パフォーマンスを比較する際には、ファネルやセグメンテーションで Flow 関連のイベントを使用することをお勧めします。Flow 関連のイベントには次のものがあります。

- User Entered Flow (ファネルのステップ 1 として、トリガーイベントを直接使用する代わりにこれを使用します)
- Flow Trip Conversion (コンバージョンイベントを直接使用する代わりに、これをステップの 1 つとして使用します)
- User Exited Flow

### Event Triggered Flow の総トリップ数が想定より少ないのはなぜですか？

ユーザーが Flows に入るのは、トリガーイベントを実行し、Flow で定義された IF 条件に一致し、トリガーイベントの実行時点で定義されたターゲットオーディエンスセグメントに属し、エントリー制限 (Flow で定義されている場合) などのその他の条件を満たした場合のみです。さらに、エントリー時点で、ユーザーがフロー内のアクティブなトリップに参加していない必要があります。

ターゲットオーディエンスがイベントベース/カスタムセグメントベースのチェックで定義されている場合、セグメントは 3 時間ごとに 1 回更新されます。そのため、後からオーディエンスに加わったユーザーは、トリガー条件に一致した場合にのみフローに入ります。

一部のユーザーを取りこぼさないよう、イベントベース/カスタムセグメントベースのチェックを使用せずにターゲットオーディエンスを定義することを検討してください。また、これらのチェックは Entry ステージの後の最初のステップとして Flows 内に組み込んでください。

### User Entered Flow/User Exited Flow が Trigger Condition のドロップダウンに表示されていますが、それを使って作成したキャンペーンがトリガーされないのはなぜですか？

現在、これらのイベントは Trigger Condition (Smart Trigger キャンペーンの IF/AND、または Flows の Entry) ではサポートされていません。

### 特定の日付でフィルタリングした場合に、Canvas ビューと Detailed Stats ビューで表示される統計が異なるのはなぜですか？

Canvas ビューは、フィルタリングした期間中にエントリーしたユーザーの統計を表示します。一方、Detailed Stats ビューは、エントリー時期に関係なくユーザーの統計を表示します。

そのため、特定の期間にエントリーしたユーザーの行動を理解することが目的の場合は、Canvas ビューの数値を使用してください。一方、フロー全体のパフォーマンス、チャネルパフォーマンス、または特定のキャンペーンのパフォーマンスを理解することが目的の場合は、Detailed Stats を使用してください。
