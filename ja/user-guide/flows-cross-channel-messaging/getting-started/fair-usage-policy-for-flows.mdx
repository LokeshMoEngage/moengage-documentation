## 概要

MoEngage Flows は共有インフラストラクチャ上で実行されており、クラスター上のすべてのワークスペースが同じ基盤の処理能力を利用しています。これまでは、1 つのワークスペースがその処理能力をどれだけ利用できるかについて、強制的な上限はありませんでした。そのため、あるワークスペースで持続的な急増が発生すると、お客様自身の使用量が通常のパターンの範囲内であっても、お客様のワークスペースを含め、同じクラスターを共有する他のすべてのワークスペースのパフォーマンスが低下する可能性がありました。

フェアユースポリシー (FUP) は、契約上の月間アクティブユーザー数 (MAU) に応じた規模で、インフラストラクチャの保証された予測可能な割り当てを各ワークスペースに提供するよう設計されています。これにより、他のワークスペースの急増によってお客様のパフォーマンスが低下することはなく、同様にお客様のワークスペースが原因となることもありません。その結果、クラスター上で何が起きているかにかかわらず、お客様のワークスペースでより一貫性があり信頼性の高いフロー処理が実現します。

<Info>
  現在、FUP の上限を超えているワークスペースは 3% 未満です。大多数のワークスペースにとって、このポリシーが日々の使用に実質的な影響を与えることはありません。
</Info>

### フローへのエントリーに個別の上限がある理由

MoEngage はすでに、Data API レイヤーでのレート制限と、月間アクティブユーザー数 (MAU) に基づく課金という 2 つの方法で使用量を管理しています。いずれも、次の特定のパターンを捕捉するようには設計されていません。

| 既存の制御 | 測定対象 | 対象外の内容 |
| --- | --- | --- |
| Data API のレート制限 | MoEngage API への個々のリクエストレート | 複数のフローで同時に発生する、持続的な高頻度のイベントトリガー |
| MAU 課金 | 追跡対象オーディエンスの規模 | 特定の 1 時間内にそれらのユーザーがどれだけ集中的にフローへのエントリーをトリガーするか |
| **Flow Entry FUP** | ローリング 60 分間のウィンドウ内でユーザーがフローに正常にエントリーするレート | これが FUP によって埋められるギャップです |

フローへのエントリー量のコストが高くなるのは、正常なエントリーの数だけが理由ではありません。バックエンドで評価されるすべての処理が関係します。正常なエントリー 1 件につき、約 11 件のトリガーイベントが処理されます (残りの約 10 件は適格性チェックに失敗しますが、それでもシステムリソースを消費します)。ユーザーがフローに入ると、ジャーニーが終了するまでにシステムは平均 20 回の判定チェック (分岐ロジック、待機条件、メッセージの適格性) を実行します。App Opened や Product Viewed のような単一の高頻度トリガーを複数のフローで設定すると、エントリー数だけから想定されるよりもはるかに多くの処理負荷が発生する可能性があります。

FUP は、ワークスペースごとに、ローリング 60 分間のウィンドウ内での正常なフローへのエントリー数に上限を設定します。FUP により、プラットフォーム上のすべてのワークスペースにとって、共有の処理能力が予測可能かつ公平になります。

<Info>
  FUP は現在、**Event-Triggered Flows** にのみ適用されます。各ワークスペースには独自の独立した上限があります。同じアカウント配下の複数のワークスペースで上限が共有されることはありません。
</Info>

## FUP の上限

FUP の上限は、ワークスペースの契約上の月間アクティブユーザー数 (MAU) から算出されます。MoEngage は各請求月の開始時に上限を自動的に再計算するため、上限は月ごとに変わる場合があります。手動での操作は必要ありません。

現在の上限と消費量を確認するには、[FUP Stats Hub](#fup-stats-hub) を開きます。

上限の拡張を購入している場合 ([FUP の上限の引き上げ](#increasing-your-fup-limit)を参照)、実質的な上限の合計は、MAU ベースの上限に購入した拡張分を加えたものになります。毎月の再計算は拡張分には影響しません。

## 上限の追跡方法

FUP では、正時での固定リセットではなく、ローリング 60 分間のウィンドウを使用します。任意の時点で、システムは直近 60 分間の正常なフローへのエントリーをすべてカウントし、上限と比較します。

**エントリーとしてカウントされるもの:**

ユーザーは、すべての適格性チェックに正常に合格した場合にのみエントリーとしてカウントされます。

- トリガーイベントが実行されている。
- ユーザーがフローのターゲットオーディエンスの基準を満たしている。
- ユーザーがフローで設定されたエントリー頻度を超えていない。

これらのチェックのいずれかに失敗したユーザーは、FUP の上限に対してカウントされません。

同じユーザーによる繰り返しのエントリーを含め、正常なエントリーはそれぞれ個別にカウントされます。ユーザーが再度条件を満たしてフローに再エントリーした場合、それは新しいエントリーとしてカウントされます。

<Note>
ユーザーが適格性チェックに失敗した場合でも、トリガーイベントの評価には処理能力が使用されます。これが上限が存在する理由ですが、上限でカウントされる対象は変わりません。FUP の上限に対してカウントされるのは正常なエントリーのみです。
</Note>

## 適用

ローリング 60 分間のウィンドウ内でワークスペースが FUP の上限に達すると、新しいフローへのエントリーは直ちにブロックされます。エントリーはキューに入れられず、再試行も自動回復もされません。

エントリーがブロックされ始める前に、チームが事前に通知を受け、フローの構成を見直す時間を確保できるよう、[Threshold Alert](#threshold-alert) を設定してください。

### ドロップされたエントリー

上限に達した後にドロップされたエントリーは回復できません。ドロップされたユーザーは、フローの再エントリー設定に従い、再度条件を満たしてエントリー条件を再トリガーした場合にのみ、フローに再度エントリーします。

## アラート

すべての FUP アラートは **Settings > Alert Management** で管理します。このページには 2 つのタブがあります。

- **System Alerts**: FUP システムアラートはデフォルトでここに自動追加されます。
- **All Alerts**: ワークスペース内のシステムアラートとカスタムアラートをまとめて表示します。

アラートの種類、サブスクリプション、アラートの管理など、Alert Management の仕組みの概要については、[Alert Management の概要](/ja/user-guide/settings/reports-and-alerts/alert-management/getting-started/overview-alert-management)を参照してください。

### Threshold Alert

これは、使用量が定義したしきい値を超えたときにチームに通知するカスタムアラートです。デフォルトでは追加されないため、作成する必要があります。

このアラートを作成するには、FUP Stats Hub で **Create Alert** をクリックします。新しいタブで Alert Management が開き、**Create Alert on** に **FUP for event triggered flows** が事前入力されています。

| パラメーター | 詳細 |
|---|---|
| デフォルトのしきい値 | FUP の上限の 75% |
| デフォルトの頻度 | 1 日 1 回 |
| 頻度の範囲 | 1 時間ごとから 10 日ごとまで |
| 受信者 | 最大 50 件のメールアドレス |

各アラートメールには次の内容が含まれます。

- ウィンドウ内で使用量が設定したしきい値を超えた回数。
- 消費量の上位 5 つのフロー (それぞれ該当するフローページへのリンク付き)。
- 同じウィンドウ内でのフローごとの抑制されたエントリー数。
- FUP Stats Hub への直接リンク。

### Limit Reached Alert (100%)

このシステムアラートはワークスペースに自動的に追加されるため、設定は不要です。ワークスペースが FUP の上限の 100% に達した時点でトリガーされ、新しいフローへのエントリーがブロックされていることを通知します。

このアラートには、フローレベルの診断の詳細は含まれません。フローごとの詳細については、Threshold Alert または FUP Stats Hub を使用してください。

このアラートには次の権限が適用されます。

| ロール | 表示可能 | 編集可能 | 自分をサブスクライブ | 他のユーザーをサブスクライブ |
|---|---|---|---|---|
| すべてのユーザー | はい | いいえ | はい | いいえ |
| 管理者 | はい | はい (サブスクライバーリストのみ) | はい | はい |

## FUP Stats Hub

FUP Stats Hub には、ワークスペースのリアルタイムおよび過去の FUP 消費量が表示されます。アクセスするには、次の手順を実行します。
1. MoEngage UI の左側のナビゲーションメニューで、**Engage** > **All Flows** をクリックします。
2. Flows ページで、**% of entries used** インジケーターをクリックして Stats Hub にアクセスします。

![右上にエントリー使用量インジケーターが強調表示された MoEngage Flows ページ。このインジケーターから FUP Stats Hub が開きます](/images/fup-stats-hub.png)

<Note>
  FUP Stats Hub には、任意の FUP アラートメールからもアクセスできます。
</Note>

ハブには次の内容が表示されます。

| コンポーネント | 説明 |
|---|---|
| Rolling 60-min consumption | 現在のローリングウィンドウで処理されたエントリーのリアルタイムのカウントを、FUP の上限と比較して表示します。 |
| Per-flow consumption | 現在または選択した期間における、フローごとのエントリー量と抑制されたエントリー数です。 |
| Forward projection | ローリング 60 分間のウィンドウが進むにつれて利用可能になるエントリーの推定数で、処理能力がいつ回復するかを示します。 |
| Historical trend | 最大 60 日間の処理されたエントリーと抑制されたエントリーのグラフです。FUP の上限ラインが重ねて表示され、毎月の上限の再計算が反映されます。より短い期間でフィルタリングすることもできます。 |
| Create Alert button | FUP アラートタイプが事前入力された状態で Alert Management を開きます。 |

## FUP の上限の引き上げ

ワークスペースが常に上限付近または上限を超えて稼働している場合は、100,000 エントリー/時間単位で、一時的または恒久的な上限の引き上げを購入できます。

引き上げをリクエストするには、カスタマーサクセスマネージャーに連絡し、次の内容を指定してください。

- 必要な 100,000 エントリー/時間単位の数。
- 開始日。
- 予定期間、または恒久的な引き上げが必要であること。

上限は、合意した開始日より前にシステムで更新されます。

購入した拡張分は加算されるため、実質的な上限の合計は常に MAU ベースの上限に購入した拡張分を加えたものになります。拡張が有効な間に MAU が変更された場合、基本の上限は再計算されますが、拡張分は変わりません。

## よくある質問

<AccordionGroup>

<Accordion title="FUP はどのフローに適用されますか？">
FUP は現在、Event-Triggered Flows にのみ適用されます。One-time Flows と Periodic Flows は対象外です。
</Accordion>

<Accordion title="FUP の上限は、アカウント内の複数のワークスペースで共有されますか？">
いいえ。各ワークスペースには独自の独立した FUP の上限があります。同じアカウント配下の複数のワークスペースで上限が共有または合算されることはありません。
</Accordion>

<Accordion title="同じユーザーが同じフローに複数回エントリーした場合、各エントリーはカウントされますか？">
はい。同じユーザーによる繰り返しのエントリーを含め、正常なエントリーはそれぞれ個別にカウントされます。
</Accordion>

<Accordion title="ドロップされたエントリーは回復できますか？">
いいえ。ドロップされたエントリーは自動的に回復できません。ユーザーは、フローの再エントリー設定に従い、再度条件を満たしてエントリー条件を再トリガーした場合にのみ、フローに再度エントリーします。
</Accordion>

<Accordion title="MAU が変更されると、FUP の上限はどうなりますか？">
基本の上限は、更新された MAU に基づいて各請求月の開始時に自動的に再計算されるため、月ごとに変わる場合があります。拡張を購入している場合、再計算は拡張分には影響しません。上限の合計は常に基本の上限に拡張分を加えたものになります。
</Accordion>

<Accordion title="MoEngage 側でインシデントが発生した場合、FUP の上限はどうなりますか？">
MoEngage 側のインフラストラクチャの問題や遅延によってキューに入ったリクエストが滞留した場合、滞留の解消が上限に対してカウントされないよう、キャッチアップ期間中は FUP が一時的に停止されます。
</Accordion>

</AccordionGroup>
