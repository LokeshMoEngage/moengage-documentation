# クライアントサイドパーソナライゼーション

## クライアントサイドパーソナライゼーションとは

クライアントサイドパーソナライゼーションとは、Web サイト訪問者の行動、好み、過去のインタラクションに基づいて、Web サイトのコンテンツをリアルタイムで調整および変更するプロセスを指します。Web サイトのページが読み込まれると、JavaScript SDK を使用してユーザーのブラウザー上で実行されます。この JavaScript コードは主に、ユーザーの識別、そのユーザー専用に作成されたパーソナライズされたエクスペリエンスの取得、および Web サイトのページへのレンダリングを行います。

## クライアントサイドパーソナライゼーションの仕組み

![クライアントサイドパーソナライゼーション](/images/moengage_aed406.png)

## クライアントサイドパーソナライゼーションのメリット

1. **ビジュアルエディター**: ほとんどのクライアントサイドパーソナライゼーションツールには WYSIWYG（What You See Is What You Get）エディターが付属しており、Web ページ内のさまざまな要素を簡単にパーソナライズできます。さらに、Web ページに埋め込むことができる既製のウィジェットも用意されているため、コードを記述する必要がありません。
2. **実装の容易さ**: 一般的に設定が簡単です。すべての Web ページに SDK が統合されるように、Web サイトに数行のコードを組み込むだけで済みます。
3. **リアルタイムの変更**: テストはユーザーのブラウザーで Web ページが読み込まれた後に実施されるため、Web ページにリアルタイムで変更を加えることができます。

クライアントサイドパーソナライゼーションを使用すると、仮説を非常に迅速にテストし、実験結果に基づいて変更をデプロイするかどうかを判断できます。

## クライアントサイドパーソナライゼーションの制限

1. **Web ブラウザーでのみ動作**: WYSIWYG ビジュアルエディターは主に Web サイトで動作します。モバイルアプリやその他のデジタルプラットフォームで同様のエクスペリエンスを設定するには、サーバーサイドパーソナライゼーションの機能が必要です。
2. **機能管理**: 新機能をユーザーベース全体に段階的に展開する制御などの高度な実験は、クライアントサイドパーソナライゼーションの手法では制御できません。
3. **ページ読み込みへの影響**: SDK の統合方法によっては、ページの読み込み時間がわずかに増加する場合があります。

## クライアントサイドパーソナライゼーションを使用する場面

- **E コマース:** 小売業者は、クライアントサイドパーソナライゼーションを使用して、ユーザーの閲覧履歴や検索行動に基づいてカスタマイズされた商品レコメンデーションを表示できます。
- **コンテンツマーケティング**: パブリッシャーは、各ユーザーの閲覧傾向や過去のエンゲージメントパターンに基づいて、表示するコンテンツをパーソナライズできます。
- **A/B テスト**: マーケターは、クライアントサイドパーソナライゼーションを使用して A/B テストを実施し、Web ページ、広告コピー、コールトゥアクションの最もパフォーマンスの高いバージョンを特定できます。
- **プロモーションオファー**: 企業はプロモーションオファーを動的にパーソナライズして、コンバージョンを促進し、顧客エンゲージメントを高めることができます。

# サーバーサイドパーソナライゼーション

## サーバーサイドパーソナライゼーションとは

サーバーサイドでは、パーソナライゼーションはサーバー側で行われます。つまり、カスタマイズされたコンテンツはサーバーで生成され、クライアント側で追加の処理を行うことなく、サーバーからユーザーのモバイルアプリ/ブラウザーに直接配信されます。これにより、ページの読み込み時間が短縮され、シームレスなユーザーエクスペリエンスが実現します。

## サーバーサイドパーソナライゼーションの仕組み

![サーバーサイドパーソナライゼーション](/images/moengage_132042.png)

## サーバーサイドパーソナライゼーションのメリット

1. **プラットフォーム間の一貫性**: アプリ、Web サイト、その他のデジタルプラットフォーム全体でシームレスなエクスペリエンスを確保し、ユーザーのデバイスやブラウザーの制限への依存をなくすには、サーバーサイドテストが最適です。
2. **速度**と**ユーザーエクスペリエンス**: 読み込み時間の改善が優先事項である場合、サーバーサイドテストが最も効果的です。サーバーからページが送信される前にバリエーションを処理するため、クライアントサイドの実験よりも読み込み時間が短く、クライアントサイドテストで発生する可能性のあるページレンダリングの遅延がありません。また、ページの読み込み中または読み込み後に変更が加えられた場合にクライアントサイドテストで発生することがあるちらつき効果も回避できます。
3. **複雑な実験**: さまざまなアルゴリズム、バックエンドプロセス、コアビジネスロジックのテストを含む複雑な実験を実施したい場合は、サーバーサイドテストが適しています。これには、商品や記事の新しいレコメンデーションアルゴリズムのテスト、新しい価格設定ロジックや新しいチェックアウトフローの試行などが含まれます。
4. **SEO フレンドリー**: コンテンツはサーバーレベルでレンダリングされてからクライアントのブラウザーに送信されるため、サーバーサイドテストはクライアントサイドテストよりも SEO に適しています。サーバーサイドテストによる変更は、検索エンジンによって適切にインデックス登録されます。
5. **セキュリティ**: ロジックはクライアントのブラウザーではなくサーバー上に存在するため、サーバーサイドテストはより安全です。追加のセキュリティ対策が必要な決済処理やアカウントログインなど、機密性の高い領域のテストに最適です。

## サーバーサイドパーソナライゼーションの考慮事項

1. **技術的な専門知識**: サーバーサイドのコードを変更する必要があるため、サーバーサイドパーソナライゼーションには一般的にクライアントサイドテストよりも高度な技術知識が必要です。そのため、熟練した開発者のリソースとサポートが必要になります。
2. **コスト**: サーバーサイドパーソナライゼーションは、一般的にクライアントサイドの代替手段と比べて、より多くの開発時間とリソースを必要とします。
3. **実験のスピード**: 迅速な反復テストを実施してすぐに結果を確認する必要がある場合は、実装スピードが速いクライアントサイドパーソナライゼーションの方が有益な場合があります。
