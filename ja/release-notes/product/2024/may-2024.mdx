# In-App キャンペーンのテスト

キャンペーンが期待どおりに表示されない理由を探る必要はもうありません。MoEngage は In-App キャンペーンのテストプロセスを強化し、実用的なフィードバックと具体的なエラーログをダッシュボード上に直接表示するようになりました。これにより、キャンペーンを公開する前に、キャンペーンのフロー全体をテストできます。

詳細については、[In-App キャンペーンのテスト](/ja/user-guide/campaigns-and-channels/in-app-message/create/test-your-in-app-campaign)を参照してください。

# Key Metrics Dashboard 3.0

データがすべてを左右する世界において、Key Metrics Dashboard 3.0 は MoEngage を業界の最前線に位置付けます。新しいダッシュボードは、インサイト主導のエンゲージメントを切り開き、データをこれまで以上に簡単にアクションへとつなげられるようにします。

これが大きな意味を持つ理由は次のとおりです。

- 効率の向上: データの整理に費やす時間を減らし、効果的なキャンペーンの作成により多くの時間を充てられるようになります。
- 実用的な戦略: インサイトをすぐに活用できるため、リアルタイムで戦略を転換し、効果を最大化してエンゲージメントを促進できます。
- 競争力の強化: ユーザーの行動をリアルタイムで理解して対応することで、競合他社に先んじて、優れたカスタマーエクスペリエンスを提供できます。

詳細については、[Key Metrics](/ja/user-guide/analyze/dashboards/key-metrics)を参照してください。

# MoEngage ダッシュボードへの「Workspace」概念の導入

今回のリリースで、MoEngage は MoEngage ダッシュボードに関する重要なアップデートを発表しました。ユーザーの理解を深め、プロジェクトの性質をより適切に表すため、*App* という用語を *Workspace* に置き換えました。

## 「Workspace」という用語を使用する理由

*Workspace* という用語は、このセクション内の機能や能力をより包括的に理解するのに役立ちます。この用語は、アプリケーションと、顧客のセグメンテーション、キャンペーンの実行、データ分析などの関連するすべてのアクティビティを包含します。多面的な幅広い作業が行われる、より包括的な空間を表しています。

何よりも、*Workspace* への用語変更は、MoEngage ダッシュボードを直感的でユーザー中心のプラットフォームにするという当社の目標により合致しています。この変更により、プラットフォーム内のコラボレーション環境がより適切に表現され、すべての関係者が戦略について話し合い、計画し、実行しやすくなると考えています。

概念を変更した主な箇所は次のとおりです。

- 新しいワークスペースの作成: Add App > Add Workspace
- General Settings: App ID > Workspace ID
- API Settings: App ID > Workspace ID

# プッシュ通知の Notification Sent、Notification Dropped、Notification Failed イベント

これらの新しいイベントを使用して、ユーザーレベルのイベントを生成し、エンドツーエンドの通知配信ファネルを可視化できるようになりました。

- Notification Sent(Android または Web): このイベントは、送信が正常に試行され、送信サービスによって受け付けられたすべてのユーザーに対して生成されます。
- Notification Dropped: このイベントは、リーチャビリティまたはキャンペーン制御の理由により、キャンペーンの送信試行の対象外となったユーザーに対して生成されます。
- Notification Failed(Android、iOS、Web): このイベントは、コンテンツまたは送信サービスレベルの理由により送信試行が失敗したユーザーに対して生成されます。

このデータを管理しやすくするため、いくつかの追加属性も追加しました。

- Reason Group: すばやくフィルタリングするための、ドロップまたは失敗の理由の大まかなカテゴリ(リーチャビリティ、キャンペーン制御、キャンペーンコンテンツ、送信失敗)
- Reason: ドロップまたは失敗の正確な理由(デバイスなし、アクティブなデバイストークンなし、フリークエンシーキャッピング(FC)、Do Not Disturb(DND)、最小遅延、未登録、クライアント接続エラーなど)
- Service: FCM、APNS、Mozilla Firefox、Google Chrome、Safari、Microsoft Edge、HMS

Reason Group と Reason の詳細については、[Push Analytics と情報](/ja/user-guide/campaigns-and-channels/mobile-push/analyze/push-analytics-and-info)を参照してください。

# カタログ更新アラート

カタログ更新アラートシステムは、カタログの更新を綿密に追跡し、更新のステータスをマーケターに即座に通知します。

フィードファイルが正常に処理されるたびに、システムは処理の完了を示すメールを送信します。重要な点として、このメールには処理結果の詳細な統計が含まれます。

処理が失敗した場合、アラートシステムはエラーメッセージを提供します。これらのメッセージは、ファイル処理中に何が問題だったかを説明し、問題の解決に役立つインサイトを提供するため重要です。

注: 今後、新しいカタログを作成すると、メールアドレスがカタログ更新アラートに自動的に登録されます。登録設定を変更するには、カタログページの上部にある **Manage alerts** セクションにアクセスしてください。

詳細については、[カタログ](/ja/user-guide/content/recommendations/getting-started/catalogs#catalog-update-alerts)を参照してください。

# 秘密鍵の構成による送信速度の変更

MoEngage は、1つのキャンペーンがプロジェクトの上限を超えないように、プッシュ通知の最大スロットル速度を 500,000 RPM に変更しました。ただし、並行して実行されるキャンペーンにより、引き続きドロップが発生する場合があります。

詳細については、[FCM 認証](https://www.moengage.com/docs/developer-guide/android-sdk/push/basic/fcm-authentication)を参照してください。

# Push Reachability ダッシュボード

リーチャビリティとは、選択したチャネルを通じてユーザーにリーチできるかどうかを示す指標です。MoEngage の Reachability ダッシュボードには、プッシュ通知の受信をオプトインしたすべてのユーザーと、オプトインしていないユーザーのリーチャビリティのトレンドが表示されます。

Push Reachability ダッシュボードでは、次の4つの KPI にわたるプッシュキャンペーンのパフォーマンスの概要を確認できます。

- プッシュ対象ユーザー
- プッシュ到達可能ユーザー
- オプトインしたユーザー
- オプトアウトしたユーザー

## 重要な理由

Android 13 の展開に伴い、ユーザーのオプトインの詳細を理解することがこれまで以上に重要になっています。このダッシュボードは、これらの指標を簡素化するだけでなく、戦略を前進させる実用的なインサイトへと変換します。

詳細については、[Android のプッシュ許可とリーチャビリティ](/ja/user-guide/campaigns-and-channels/mobile-push/notification-features-and-behavior/android-push-permission-and-reachability)を参照してください。

# テンプレートをプリセットとして保存

数え切れないほどの下書きテンプレートの作成と保存や、一度選択したエディターを切り替えられないという制限に不満を感じていませんか?

これらの問題に対処するため、MoEngage は次の方法で OSM のエクスペリエンスを強化しました。

- すべてのテンプレートを1か所で確認できる、一覧ページの新しい UI を作成しました。
- 下書きを保存する必要はもうありません。ダッシュボードにテンプレートを直接保存できるようになりました。

詳細については、[OSM のカスタマイズされたテンプレートの保存](/ja/user-guide/campaigns-and-channels/on-site-message/create/saving-customized-templates-for-osm)を参照してください。
